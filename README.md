# Лабораторная работа №2: индексирование и алгоритмы поиска

Консольное приложение на C++23 для хранения набора объектов `Student`, построения нескольких индексов и сравнения линейного, древесного и бинарного поиска.

Проект является продолжением ЛР-1: `BinarySearchTree`, `DynamicArray` и модель `Student` повторно используются из репозитория [AD3](https://github.com/VenEraBle842/AD3.git). Зависимость загружается через CMake `FetchContent` и зафиксирована на неизменяемой ревизии `406eff221ae7db82aef6d9ccfec0360203600aaa`. Локальная копия `TreeSetLab` для сборки не нужна.

## Возможности

- Каноническое хранилище студентов на собственном `DynamicArray<Student>`.
- Проверка уникальности стабильного идентификатора `Student::id`.
- Фиксированный каталог индексов по ID, фамилии, году рождения, GPA и составному ключу.
- `TreeDictionary<TKey, TValue>` поверх бинарного дерева поиска ЛР-1.
- `ArraySortedSequence<T, Compare>` поверх собственного динамического массива ЛР-1.
- Самостоятельно реализованные `lowerBound`, `upperBound`, `binarySearch`, `equalRange` и `rangeSearch`.
- Точный поиск по всем индексируемым атрибутам.
- Включительный диапазонный поиск по году рождения и GPA.
- Точный и лексикографический диапазонный поиск по составному ключу.
- Линейная, древесная и бинарная стратегии на одном неизменяемом наборе данных.
- Контроль состояний индексов: не построены, актуальны или устарели.
- Версионированный человекочитаемый формат данных с транзакционной загрузкой.
- Безопасное сохранение через временный файл и последующую замену целевого файла.
- Воспроизводимый бенчмарк с прогревом, медианой, проверкой результатов и CSV-экспортом.
- Интерактивное меню для ручного и автоматического ввода, поиска, файловых операций и измерений.
- Модульные и интеграционные тесты GoogleTest, конфигурация ASan/UBSan.

Исходные записи никогда не сортируются и не переставляются. Индексы строятся отдельно, поэтому позиция студента в исходной последовательности не используется как внешний идентификатор.

## Архитектура

```text
Console UI
    |
    v
StudentSearchService
    |-- StudentRepository --------> structured text storage
    |       `-- DynamicArray<Student>
    |
    `-- StudentIndexCatalog
            |-- TreeDictionary indexes
            |       `-- BinarySearchTree from AD3
            |
            `-- ArraySortedSequence indexes
                    `-- DynamicArray from AD3

BenchmarkRunner ------------------> CSV
```

`StudentSearchService` является единым фасадом для изменения данных, построения индексов и выполнения запросов. `StudentRepository` владеет исходными объектами, а `StudentIndexCatalog` хранит только ключи, позиции и `RecordId`.

После любого изменения репозитория версия данных увеличивается и назначается новый уникальный идентификатор снимка. Каталог запоминает этот идентификатор при построении и не разрешает пользоваться индексом другого снимка, даже при совпадении счётчиков версий. Копия репозитория сохраняет идентификатор снимка до первого изменения, перемещение переносит его вместе с данными и оставляет источник пустым с новым идентификатором. Линейный поиск продолжает работать непосредственно по актуальным исходным данным.

## Модель данных

`Student` импортируется из ЛР-1 и содержит:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `std::uint64_t` | Уникальный и стабильный идентификатор записи |
| `firstName` | `std::string` | Имя |
| `lastName` | `std::string` | Фамилия |
| `birthYear` | `int` | Год рождения |
| `gpa` | `double` | Конечное значение среднего балла |

Повторный `id` отклоняется как `RepositoryError::DuplicateId`. Значения GPA `NaN`, `+inf` и `-inf` не принимаются файловым слоем, интерфейсом и репозиторием (`RepositoryError::InvalidGpa`). Добавление и пакетная замена проверяют GPA до изменения хранилища. Неконечные ключи и границы GPA отклоняются сервисом как `ServiceError::InvalidKey`, каталогом — как `IndexError::InvalidKey` или `SearchError::InvalidKey`.

Составной ключ имеет отдельный тип:

```cpp
struct StudentCompositeKey {
    std::string lastName;
    std::string firstName;
    int birthYear;
};
```

Ключи сравниваются лексикографически: сначала фамилия, затем имя, затем год рождения. Эквивалентность определяется компаратором: ни один ключ не должен быть меньше другого.

## Каталог индексов

За один проход по репозиторию строятся следующие древесные индексы:

| Индекс | Ключ | Значение | Запросы |
| --- | --- | --- | --- |
| `id` | `RecordId` | Позиция в репозитории | Точный |
| `lastName` | `std::string` | `DynamicArray<RecordId>` | Точный |
| `birthYear` | `int` | `DynamicArray<RecordId>` | Точный и диапазонный |
| `gpa` | `double` | `DynamicArray<RecordId>` | Точный и диапазонный |
| `composite` | `StudentCompositeKey` | `DynamicArray<RecordId>` | Точный и лексикографический диапазонный |

Для бинарного поиска параллельно строятся отсортированные последовательности `IndexEntry<Key>`. Каждая запись последовательности содержит ключ и `RecordId`. Даже если несколько студентов имеют одинаковый атрибут, в последовательности остаётся отдельная запись на каждого студента.

Результаты упорядочиваются сначала по ключу, затем по `RecordId`. Внутри группы одного древесного ключа идентификаторы также поддерживаются в возрастающем порядке. Один студент не может дважды появиться в результате одного запроса.

## `TreeDictionary<TKey, TValue>`

`TreeDictionary` реализует интерфейс `IDictionary` и использует `BinarySearchTree` из AD3. В узле дерева хранится `std::shared_ptr<DictionaryEntry<TKey, TValue>>`, а компаратор сравнивает только ключи записей.

Основные операции:

```cpp
#include "dictionary/tree_dictionary.hpp"

TreeDictionary<int, std::string> dictionary;

auto added = dictionary.add(10, "ten");
auto duplicate = dictionary.add(10, "other");

auto value = dictionary.find(10);                // optional<string> с копией
bool updated = dictionary.update(10, "TEN");

DynamicArray<int> keys = dictionary.getKeys();
bool removed = dictionary.remove(10);
```

`add` возвращает `std::expected<void, DictionaryError>` и сообщает `DuplicateKey` для повторного ключа. `find` возвращает `std::optional<TValue>` с независимой копией значения, `update` заменяет существующее значение, а `remove` возвращает `false` при отсутствии. Штатное отсутствие ключа не выпускает наружу `NodeNotFoundException` ЛР-1.

Для внутренних алгоритмов, которым нужно изменить значение без копирования и без второго обхода дерева, `TreeDictionary` предоставляет шаблонный `modify(key, callback)`. Обработчик вызывается только при найденном ключе, а наружу возвращается `bool`.

`getKeys()` и `getValues()` используют симметричный обход `LKP`, поэтому порядок определяется компаратором. `getCapacity()` для дерева возвращает `std::nullopt`.

Копирование словаря выполняет глубокое копирование записей. Изменение значения в копии не влияет на исходный словарь. Перемещённый источник остаётся корректным пустым объектом.

Сложность поиска, вставки и удаления — $O(h)$, где $h$ является высотой дерева. Дерево ЛР-1 не балансируется:

- в среднем при удачном порядке ключей — $O(log N)$;
- в вырожденном дереве — $O(N)$;
- последовательная вставка возрастающих или убывающих ключей может потребовать $O(N^2)$ суммарного времени.

## `ArraySortedSequence<T, Compare>`

`ArraySortedSequence` реализует `ISortedSequence` и хранит элементы в `DynamicArray<T>` ЛР-1. Готовая сортировка не вызывается: `add` находит позицию общей функцией `upperBound`, `indexOf` использует общий `binarySearch`, после чего при вставке элементы собственного массива сдвигаются вправо. Собственной дублирующей реализации бинарных границ внутри последовательности нет.

```cpp
#include "sequence/array_sorted_sequence.hpp"

ArraySortedSequence<int> sequence;
sequence.add(4);
sequence.add(1);
sequence.add(4);

// 1, 4, 4
auto first = sequence.getFirst();
auto last = sequence.getLast();
auto position = sequence.indexOf(4);
auto middle = sequence.getSubsequence(1, 2);
```

Последовательность допускает эквивалентные элементы. `get`, `getFirst` и `getLast` возвращают независимое значение через `std::optional<T>`, а `indexOf` — необязательный индекс. Метод `at` даёт быстрый доступ только для чтения по уже проверенному индексу и использует проверку границ `DynamicArray::at`. Ошибочный диапазон подпоследовательности возвращает `SequenceError::InvalidRange` через `std::expected`.

Сложности:

| Операция | Сложность |
| --- | --- |
| Поиск позиции | $O(log N)$ |
| Вставка в конец без расширения массива | $O(log N)$ |
| Вставка со сдвигом или расширением массива | $O(N)$ |
| Доступ по индексу | $O(1)$ |
| Поиск `indexOf` | $O(log N)$ |

## Бинарный поиск

Алгоритмы из `search/binary_search.hpp` работают с любой последовательностью, удовлетворяющей концепту индексируемой последовательности, извлекателем ключа и строгим компаратором.

```cpp
#include "search/binary_search.hpp"
#include "sequence/array_sorted_sequence.hpp"

ArraySortedSequence<int> values;
values.add(1);
values.add(3);
values.add(3);
values.add(5);

std::size_t first = lowerBound(values, 3);       // 1
std::size_t after = upperBound(values, 3);       // 3
auto found = binarySearch(values, 5);            // optional{3}
auto allThrees = equalRange(values, 3);          // TwoElement{1, 3}
auto positions = rangeSearch(values, 2, 5);      // индексы 1, 2, 3
```

Алгоритмы не делегируют работу `std::lower_bound`, `std::upper_bound` или `std::binary_search`.

Общий цикл деления диапазона реализован один раз в `binaryPartitionPoint`. Функции `lowerBound` и `upperBound` передают ему разные предикаты границы, поэтому управление бинарным диапазоном не дублируется.

- `lowerBound` возвращает первую позицию с ключом не меньше заданного.
- `upperBound` возвращает первую позицию с ключом больше заданного.
- `binarySearch` возвращает позицию одного совпадения или `std::nullopt`.
- `equalRange` возвращает полуинтервал всех эквивалентных ключей через собственный `TwoElement`.
- `rangeSearch` возвращает позиции всех записей в замкнутом диапазоне `[lower, upper]`.

Поиск границы занимает $O(log N)$, а получение всех `k` совпадений — $O(log N + k)$. Обратный диапазон возвращает `SearchError::InvalidRange`; корректный пустой результат ошибкой не является.

## Сервис поиска

Типичный сценарий программного использования:

```cpp
#include "service/student_search_service.hpp"

StudentSearchService service;
service.addStudent(Student{101, "Ivan", "Ivanov", 2003, 4.8});
service.addStudent(Student{102, "Anna", "Ivanova", 2002, 4.5});
service.buildIndexes();

auto byName = service.findByLastName("Ivanov", SearchStrategy::Tree);
auto byYear = service.findBirthYearRange(2001, 2003, RangeStrategy::Binary);
auto composite = service.findByComposite(
    StudentCompositeKey{"Ivanov", "Ivan", 2003},
    SearchStrategy::Binary
);
```

Для точного поиска доступны:

| Стратегия | Реализация |
| --- | --- |
| `SearchStrategy::Linear` | Последовательный просмотр исходного `DynamicArray<Student>` |
| `SearchStrategy::Tree` | Поиск в `TreeDictionary` |
| `SearchStrategy::Binary` | Поиск границ в `ArraySortedSequence` |

Для диапазонного поиска доступны `RangeStrategy::Linear` и `RangeStrategy::Binary`. Древесный индекс для диапазона намеренно не используется.

Линейная стратегия сначала собирает совпадения, затем упорядочивает только результат собственной итеративной сортировкой кучей. С учётом обязательного порядка выдачи её сложность — $O(N + k \log k)$, где `k` — число совпадений. Исходные записи не сортируются; квадратичной вставки каждого совпадения в результат нет.

`verifyLastName` и `verifyBirthYearRange` запускают разные стратегии на одном наборе и сравнивают итоговые `RecordId`. Расхождение возвращает `ServiceError::VerificationFailed`.

Попытка индексированного поиска до построения индексов возвращает `IndexNotBuilt`, а после изменения репозитория — `IndexStale`. Для восстановления достаточно вызвать `buildIndexes()`.

## Формат файла данных

Основной формат является текстовым, версионированным и пригодным для ручного просмотра:

```text
DOR2_STUDENT_DATA 1
3
101:"Ivan":"Ivanov":2003:4.8
102:"Petr":"Petrov":2002:4.2
103:"Anna":"Sidorova":2004:5
```

Первая строка содержит сигнатуру и номер версии. Вторая строка задаёт точное число последующих записей. Студент записывается в потоковом формате ЛР-1:

```text
id:"firstName":"lastName":birthYear:gpa
```

Имена и фамилии обязательно заключаются в двойные кавычки. Формат `std::quoted` поддерживает пробелы, двоеточия, кавычки и обратные слеши внутри строк. Числа используют классическую локаль с точкой как десятичным разделителем. GPA записывается с точностью, достаточной для точного восстановления `double`.

При загрузке проверяются:

- сигнатура и версия;
- корректность строки с количеством;
- наличие ровно объявленного числа записей;
- потоковый формат каждого студента;
- уникальность всех ID;
- конечность GPA;
- отсутствие лишних непробельных данных после записей.

Ошибка содержит код, сообщение, путь и номер строки, если он известен. Поддерживаются категории `OpenFailed`, `ReadFailed`, `WriteFailed`, `InvalidHeader`, `UnsupportedVersion`, `InvalidRecord`, `RecordCountMismatch`, `TrailingData` и `DuplicateId`.

Загрузка сначала полностью разбирает данные во временный массив. Репозиторий заменяется только после успешной проверки всего файла, поэтому частичная загрузка невозможна.

При сохранении данные сначала записываются в файл `<target>.tmp`. Поток проверяется после записи, сброса и закрытия. Только после этого временный файл переименовывается в целевой; при ошибке временный файл удаляется.

Индексы на диск не записываются. После загрузки они заново строятся из канонических данных.

## Бенчмарк

Автономный Release-бенчмарк:

```bash
cmake -S . -B build-release -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DDOR2_BUILD_TESTS=OFF
cmake --build build-release --parallel
./build-release/dor2_benchmark
```

По умолчанию используются:

- размер набора — 1000;
- число запросов — 200;
- seed — 42;
- выходной файл — `benchmark_results.csv`.

Другие значения можно задать в пункте `11` консольного приложения, а путь CSV — в пункте `12`.

Размер набора и число запросов ограничены 10000 каждый, их произведение — 10000000. Ограничения действуют также в программном API: `run` и `runAndSave` возвращают `std::expected<DynamicArray<BenchmarkResult>, BenchmarkFailure>`, при недопустимой нагрузке — `BenchmarkError::InvalidWorkload`. Ошибка подготовки студентов или построения измеряемого дерева возвращается как `PreparationFailed`; запуск прекращается, результаты не экспортируются. Ошибки CSV в `runAndSave` имеют категорию `FileOperationFailed` и сохраняют исходную `FileFailure`.

Для каждого запуска рассматриваются три порядка входных ключей:

- возрастающий;
- убывающий;
- псевдослучайный, воспроизводимый по seed.

Порядки формируются непосредственно генератором, без готовой сортировки. Один набор ключей и один набор запросов передаются всем сравниваемым алгоритмам. Построение измеряется отдельно для `TreeDictionary<int, std::size_t>` и `ArraySortedSequence<int>`; уничтожение структур не входит в этот интервал. Поисковые операции выполняются через `StudentSearchService` по полю `birthYear` синтетических студентов с ключами от `0` до `N-1` и стабильным `RecordId = key + 1`. Эти ключи служат для измерений и не моделируют реальные календарные годы. Создание студентов и построение каталога выполняются до измерения поиска.

Измеряются семь комбинаций для каждого порядка, всего 21 строка:

1. построение `TreeDictionary`;
2. построение `ArraySortedSequence`;
3. линейные точные запросы;
4. древесные точные запросы;
5. бинарные точные запросы;
6. линейные диапазонные запросы;
7. бинарные диапазонные запросы.

Точные запросы содержат успешные и неуспешные случаи. Диапазонные запросы содержат пустые, малые и большие результаты. Оба набора запросов создаются до измерений. Для каждого запроса предварительно сравниваются полные упорядоченные списки `RecordId`, а не суммарное число совпадений; при расхождении строки соответствующей операции получают `Verified=false`. Автономное приложение в этом случае завершает работу с ошибкой.

В поисковый интервал входят создание результата сервисом, упорядочение при линейной стратегии и обход всех возвращённых идентификаторов. Контрольная сумма каждого повтора передаётся в `volatile`-приёмник за пределами интервала, чтобы результат вычисления использовался при оптимизации Release-сборки.

Каждая операция предварительно прогревается, затем выполняется пять раз. В CSV записывается медиана времени в микросекундах. Отладочный вывод в измеряемый интервал не входит.

Формат CSV:

```text
DatasetSize,InputOrder,Algorithm,Operation,QueryCount,ElapsedUs,MatchCount,Seed,Verified
1000,Ascending,TreeDictionary,Build,1,1407.81,1000,42,true
```

Поля:

| Колонка | Содержание |
| --- | --- |
| `DatasetSize` | Размер исходного набора |
| `InputOrder` | `Ascending`, `Descending` или `Random` |
| `Algorithm` | Измеряемая структура или алгоритм |
| `Operation` | `Build`, `ExactSearch` или `RangeSearch` |
| `QueryCount` | Число запросов; для построения — 1 |
| `ElapsedUs` | Медианное время в микросекундах |
| `MatchCount` | Число построенных элементов или найденных совпадений |
| `Seed` | Seed генератора |
| `Verified` | Совпали ли результаты сравниваемых реализаций |

## Построение графика

Установите `matplotlib`, затем выполните:

```bash
python3 benchmark/plot_results.py benchmark_results.csv benchmark_plot.png
```

Первый аргумент задаёт исходный CSV, второй — имя PNG. Если аргументы не указаны, используются `benchmark_results.csv` и `benchmark_plot.png`.

PNG содержит три отдельные диаграммы: построение структур, точный поиск и диапазонный поиск. Столбцы сгруппированы по порядку входных данных, алгоритмы имеют постоянные цвета и числовые подписи. Построение показано в микросекундах на одну структуру; время поиска — как медиана времени серии, делённая на число запросов. У каждой диаграммы своя шкала; при разбросе от 50 раз применяется явно подписанная логарифмическая шкала. Для нулевого числа запросов выводится `N/A`.

Скрипт принимает один полный запуск (21 измерение, один размер набора и seed) и отклоняет строки с `Verified=false`, дубликаты и некорректные значения. Если Matplotlib установлен в локальной `.venv`, запускайте скрипт через `.venv/bin/python`.

## Обработка ошибок

Ожидаемые ситуации возвращаются значением и не требуют исключений:

| Слой | Результат |
| --- | --- |
| Словарь | `std::expected<void, DictionaryError>` |
| Отсортированная последовательность | `std::optional` и `std::expected<..., SequenceError>` |
| Бинарный поиск | `std::optional` и `std::expected<..., SearchError>` |
| Репозиторий | `std::expected<void, RepositoryError>` |
| Каталог индексов | `std::expected<..., IndexError>` |
| Сервис | `std::expected<..., ServiceError>` |
| Файловый слой | `std::expected<..., FileFailure>` |

Исключение `NodeNotFoundException` дерева ЛР-1 перехватывается на границе `TreeDictionary` после единственного поиска. Предварительный дополнительный обход через `contains` не выполняется.

Исключения остаются возможны для ошибок выделения памяти и нарушений внутренних инвариантов, после которых безопасное продолжение невозможно.

## Ограничения реализации

- Бинарное дерево не балансируется.
- Индексы существуют только в памяти и не сохраняются в файл.
- Схема индексов фиксирована во время компиляции.
- Графического интерфейса нет.
- Конкурентное изменение данных и многопоточный поиск не поддерживаются.
- B/B+-деревья, прошитые деревья и хеш-таблицы не реализуются.

В производственном коде ЛР-2 намеренно не используются готовые контейнеры `std::vector`, `std::list`, `std::deque`, `std::map`, `std::set`, `std::unordered_map`, `std::unordered_set` и их аналоги. Также не используются `std::pair`, `std::tuple`, готовая сортировка и стандартные алгоритмы бинарного поиска.

Для двухэлементных результатов применяется `TwoElement<TFirst, TSecond>`, для предметных записей — именованные структуры. Владение ресурсами выражено через RAII и умные указатели; сырого `new`/`delete` и владеющих сырых указателей в ЛР-2 нет.

## Подключение ЛР-1

Исходный CMake-файл зафиксированной версии AD3 предназначен для самостоятельной сборки и безусловно создаёт приложение, тесты и бенчмарк. Чтобы не добавлять эти цели в DOR2 и не делать тесты ЛР-1 обязательными, используется изолированное подключение:

1. `FetchContent` загружает репозиторий на точном commit hash.
2. Каталог исходников ЛР-1 не добавляется через его `CMakeLists.txt`.
3. DOR2 создаёт интерфейсную цель `treesetlab_core` и псевдоним `TreeSetLab::Core`.
4. Цель экспортирует только корневой include-путь AD3.
5. `dor2_core` связывается с `TreeSetLab::Core`.

Таким образом, проект собирается без локального `TreeSetLab`, не создаёт лишние цели ЛР-1 и всегда использует одну и ту же ревизию зависимости.
